Where the data comes from

The CISA Known Exploited Vulnerabilities (KEV) catalog lists vulnerabilities that the U.S. Cybersecurity and Infrastructure Security Agency has confirmed are being exploited by attackers. Most published CVEs are never exploited; the ones in KEV are, which makes the catalog one of the best signals for what to patch first.

Reading the tables

CVE
The vulnerability's ID. It links to its entry in the U.S. National Vulnerability Database (NVD); “CISA” links to the official KEV record.
Added
The date CISA added the vulnerability to KEV, meaning the date exploitation was confirmed, not the date the flaw was discovered.
Federal due date
The deadline for U.S. federal civilian agencies to fix the vulnerability under Binding Operational Directive 22-01. It doesn't bind other organizations, but it's a useful benchmark for urgency.
Ransomware use
“Known” means CISA has evidence the vulnerability was used in a ransomware campaign. “Not known” means there's no public evidence yet, not that it is safe.

What's coming

  • Exploit likelihood: FIRST EPSS scores estimating how likely each CVE is to be exploited in the next 30 days.
  • Severity: CVSS scores and weakness types from the NVD.
  • Prioritization: each CVE matched against the asset inventory of a fictional regional hospital, with a 0–100 priority score and a breakdown of where every point comes from.
  • Daily briefing: a short AI-written summary for security teams and leadership. The AI may use only the data on this site, and an automatic check flags any CVE ID it mentions that isn't in the data.

Limitations

  • This is an independent educational project, not an official source. Confirm details with CISA and NIST before acting on them.
  • The site is updated once a day, so very recent KEV additions may take up to a day to appear.
  • The hospital used for prioritization is fictional. Its scores show the method; your organization's priorities depend on what you actually run.

How it's built

A Python pipeline downloads the KEV feed, stores it in SQLite and generates these pages as plain HTML. GitHub Actions runs the tests and the pipeline every day and publishes the result to GitHub Pages. There is no server, no analytics and no cookies.
